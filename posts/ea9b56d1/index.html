Vibe Coding 范式：UI 先行，用 AI 从 0 到 1 打磨一款 App

发表于2026-09-13|更新于2026-09-15|AI
|总字数:3.9k|阅读时长:13分钟|浏览量:

前言

Vibe Coding 不是"把需求扔给 AI 然后祈祷"。它有范式，有节奏，有先后顺序。这条笔记的核心原则是：

UI 与视觉先行（mock 数据快速定型产品形态），数据与逻辑收尾（UI 定稿后再做工程化接通），细节提质贯穿全程。

为什么 UI 先行？

  • 产品形态看得见才好判断。界面没定型之前，任何数据工程投入都可能被 UI 改版推翻——先做数据，界面一改，清洗脚本、表结构、服务层跟着返工；
  • 改 UI 的成本几乎为零。此阶段全部用 mock 数据，不满意就随手改，不用迁就真实数据的格式；
  • UI OK 之后，数据工程一次投入、一次接通。此时字段需求已经完全明确（界面就是字段清单），Anki 清洗、SQLite、服务层照着界面做，不会对不上号。

如果你的数据格式已经完全定死（比如严格对接既定协议），反过来"数据先行"也成立。这里选 UI 先行，因为它对"产品还在改"的早期阶段更友好。

这条笔记以我开发日语学习 App kogo（コゴ）（N1-N5 学习软件，Expo + React Native）为例，把 Vibe Coding 一个完整软件的流程做成范式。你换成任何 App，流程不变。

角色分工：给 AI 排好座位

这套范式里有两类 AI：外部 AI（ChatGPT）当军师负责编排指挥，编程 Agent（Claude Code / OpenCode）里的插件负责执行。

角色承担工具职责
流程指挥官（军师）外部 AI（ChatGPT）初稿润色；结合 Impeccable 的 24 个指令编排设计步骤，逐步下达"下一步"
首席 UI/UX 设计师与视觉审查官Impeccable（编程 Agent 内）产品规范（init）、页面规划（shape）、代码生成（craft）、视觉迭代、动效、无障碍审查
首席工程师Superpowers（编程 Agent 内，UI 定稿后进场）技术架构文档、数据清洗脚本、DB/音频服务层，全程 TDD

分工口诀：

  • 外部 AI 出主意——润色初稿、编排 24 个指令的执行顺序，指挥节奏；
  • Impeccable 出皮——UI 先行，mock 数据快速定型所有页面；
  • Superpowers 出骨——UI OK 后进场，brainstorming → writing-plans → TDD 实现 → code review 把数据和逻辑接进来。

Superpowers 的安装与技能清单见我之前的《给 AI 编程助手装上「超能力」》，本文只讲它怎么嵌进 Vibe Coding 流程。

第一阶段：初稿与外部 AI 润色（先想清楚）

在碰任何工具之前，先手写一份初稿——不用讲究格式，功能清单、模块划分、想到什么写什么，几十行 markdown 就够。以 kogo 为例：

把润色后的大纲存进仓库，比如 docs/outline.md——它就是下一阶段的输入。

范式要点：初稿可以糙，但必须你自己写。 外部 AI 只负责查漏补缺，产品想做成什么样，决定权在你。

第二阶段：初始化产品与设计规范（init）

拿着润色后的大纲，回编程 Agent 运行 Impeccable 的初始化（注意：该命令在不同版本间改过名——最新版叫 /impeccable init，旧版（v2.x）叫 /impeccable init，网上教程两种写法都有，作用相同）：

它默认是交互式的：采访你的产品定位、用户、品牌个性、无障碍需求，最后写出 PRODUCT.md（战略层：谁用、为什么用）与 DESIGN.md（视觉层：长什么样）。命令名后面的所有文字都会作为目标上下文传入，而 init 的原则是"只问代码库和已有材料里推不出来的问题"——大纲写得越完整，采访轮次越少；信息全齐时它会直接给出草稿让你确认（写文件前一定让你点头，不会静默覆盖已有文件）。

无论走交互采访还是喂文档，都要确保它拿到这些信息：

  • 产品定位：日语 N1-N5 学习软件 kogo（コゴ），极简、高效、专注沉浸。
  • 主要模块：四大 Tab 屏（学习主页、训练页、错题回顾页、我的页）。
  • 特殊 UI/UX 需求：
    • 假名注音（Furigana / 振仮名）渲染支持
    • 音频/图片媒体卡片交互（播音反馈、看图测验）
    • 移动端（iOS/Android）原生体验，基于 Expo + NativeWind

常见问题：init 之后觉得设计不合适，需要二次调整吗？

必须调整。 /impeccable init 生成的只是 AI 基于大纲给出的"第一版草稿"，不是不可动摇的最终定稿。

为什么必须二次调整：

  • 业务细节补全：AI 在初始化时会自行填充很多"看起来合理"的逻辑，但这些假设往往缺乏你对具体业务场景、用户偏好或技术限制的理解；
  • 规避重构成本：带着不合格的设计进入代码生成阶段，后续微小的逻辑修改都会引发大量组件或接口的重构。

高效二次调整的姿势：

  1. 直接修改源文件：打开 PRODUCT.md / DESIGN.md，手动修正核心流程、交互逻辑与数据结构；
  2. 精准指令覆盖：针对不满意的点向 AI 发出具体指令（例如："修改用户注册流程，移除邮箱验证，改为纯手机号加验证码登录"），要求它同步更新设计文档；
  3. 重点审查边界：主流程逻辑是否通畅、异常状态是否有定义、页面元素是否冗余或缺失。

在产品设计阶段多花 5 分钟精雕细琢，能省去后续写代码时几小时的反复扯皮。确定设计符合预期后，再进入下一阶段。

第三阶段：外部 AI 编排，逐指令打磨 UI（重头戏）

init 完成后，回到 ChatGPT，把产出贴给它，让它当你的流程编排者——结合 Impeccable 的 24 个指令，一步步指挥你完成整个 UI 设计。

第四阶段：UI OK 之后的 Superpowers 工程化（收尾接骨）

UI 定稿、mock 数据的字段需求完全明确之后，Superpowers 进场，把真实数据与逻辑接进来。注意：Superpowers 没有斜杠命令，直接在对话框里说需求，相关技能会自动触发。

总结：Vibe Coding 指南针

步骤任务内容推荐工具 / 指令交付物
Phase 1初稿撰写与外部 AI 润色ChatGPT（或其他外部 AI）docs/outline.md
Phase 2初始化产品与设计规范/impeccable init（旧版曾叫 teach）PRODUCT.md, DESIGN.md
Phase 3编排式 UI 设计执行ChatGPT 编排 + /impeccable shape ➔ craft ➔ harden ➔ polish四大 Tab 定型 UI（mock 数据）
Phase 4技术架构与数据工程Superpowers（brainstorm → plan → TDD）ARCHITECTURE.md, kogo.db, 服务层
Phase 5mock 替换真实数据Superpowers + Impeccable 微调具备原生 App 质感的成品

按照这个顺序，你既不会在界面反复改版中返工数据层，也不会写出"充满了 AI 垃圾感"的劣质界面——因为 UI 由 Impeccable 一步步打磨，工程由 Superpowers 带着测试收尾。
